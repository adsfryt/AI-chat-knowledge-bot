# Пользовательские истории (User Stories)

## US-01: Задание вопроса боту через чат-интерфейс
**Контекст (User Story): Как Пользователь (Сотрудник или Клиент).**
> Я хочу задавать вопросы ассистенту в чате и получать текстовые ответы в режиме потоковой передачи.
> Чтобы мгновенно находить точную информацию по регламентам и материалам компании без ручного поиска по документам.

> N - некие переменные, которые неизвестны на данном этапе развития.

### Функциональные требования (FR)
- [FR-01.1] Система должна принимать текстовый запрос пользователя длинной от 1 до N символов.
- [FR-01.2] Система должна выполнять семантический поиск по векторной базе знаний и передавать релевантный контекст в LLM-модель (RAG-пайплайн).
- [FR-01.3] Система должна отображать ответ LLM в интерфейсе чата в режиме реального времени (стриминг по протоколу WebSocket).
- [FR-01.4] При отсутствии релевантного контекста в базе знаний система должна корректно информировать пользователя о невозможности дать ответ на основе загруженных материалов, не додумывая факты.

### Детализированный Use Case 
- Название: Задать вопрос по базе знаний
- Актор: Пользователь
- Предусловия:
  - Чат-интерфейс загружен и доступен.
  - В базе знаний индексирован хотя бы один файл со статусом Обработан.
- Постусловия:
  - Успех: Ответ бота отображен в окне чата, сформирован контекст, запись о сообщении сохранена в истории диалога.
  - Неудача: Состояние базы знаний не изменилось, пользователь увидел понятное сообщение об ошибке (например, «Сервис временно недоступен»).  

### Основной поток:   
- Пользователь вводит текст вопроса в поле ввода чата и нажимает кнопку «Отправить».
- Система валидирует сообщения.
- Система преобразует вопрос в векторное представление (эмбеддинг) и ищет K наиболее релевантных фрагментов в векторной БД.
- Также начинается поиск найболее релевантых документов, используя стандартные алгоритмы.
- Система формирует промпт для LLM, объединяя найденный контекст и вопрос пользователя.
- Система начинает стриминг генерации текста от LLM в окно чата символ за символом.
- По завершении генерации система сохраняет сообщение в истории диалогов.   

### Альтернативные и исключительные потоки:   
- Введено пустое сообщение или текст длиннее N символов:
  - Система блокирует кнопку отправки и выводит подсказку: «Сообщение должно содержать от 1 до N символов».
- В базе знаний не найдено релевантных фрагментов (порог сходства < определенный коэффициент):
  - Система формирует ответ: «К сожалению, в базе знаний компании нет информации для ответа на данный вопрос». Сценарий завершается.
- Превышен таймаут ответа от LLM API или произошел сбой сети:
  - Система прекращает ожидание и выводит сообщение: «Не удалось получить ответ от нейросети. Попробуйте повторить запрос позже». Сценарий завершается. 

### Критерии приемки 
* **AC-01.1 (BDD — Негативный сценарий):**
  * **Given:** Пользователь находится в чате и ввел сообщение длиною N+10 символов.
  * **When:** Пользователь нажимает кнопку «Отправить».
  * **Then:** Система НЕ отправляет запрос на бэкенд, блокирует кнопку отправки и отображает текст ошибки: «Превышен лимит символов (максимум N)».
* **AC-01.2 (BDD — Позитивный сценарий):**
  * **Given:** В базу знаний загружен регламент «Правила оформления отпусков.pdf».
  * **When:** Пользователь отправляет вопрос «Сколько дней отпуска положено в год?».
  * **Then:** Система находит соответствующий фрагмент и начинает отображать текстовый ответ языковой модели.
* **AC-01.3 (Чек-лист):**
  * [x] Сообщение пользователя сохранился в истории чатов.
  * [x] Во время ожидания первого токена ответа отображается индикатор генерции текста.

> N1, n1 - некие переменные, которые неизвестны на данном этапе развития.

### Нефункциональные требования
* **[NFR-01.1] Время отклика:** Время до появления первого токена ответа не должно превышать n1 секунд при 95-м процентиле (p95).
* **[NFR-01.2] Нагрузка:** Чат-интерфейс должен выдерживать до N1 одновременных активных стриминговых сессий.

## US-02: Загрузка и транскрипция мультимедийных файлов
**Контекст (User Story):**
> Администратор базы знаний хочет загружать аудиофайлы, изображения и видеозаписи в админ-панель,  
> Чтобы система автоматически распознавала речь (транскрибировала её в текст) и индексировала содержание медиафайлов в векторной базе.

> M,J - некие переменные, которые неизвестны на данном этапе развития. M > 10 </br>
> форматов* - точный список форматов на данном этапе не опрелен.

### Функциональные требования (FR)
* **[FR-02.1]** Система должна принимать медиафайлы опрделенных форматов* размером до M МБ через drag-and-drop интерфейс.
* **[FR-02.2]** Для видеофайлов система должна автоматически извлекать аудиодорожку до передачи в модуль распознавания речи, а видое разбивается на набор изображений.
* **[FR-02.3]** Для аудиофайлов система должна выполнять автоматическую транскрипцию аудио в текст при помощи модуля распознавания речи.
* **[FR-02.4]** Для изображений система выполняет алгоритмы поиска текста и преобразование в векторные эмбеддинги.
* **[FR-02.5]** Система должна разбивать полученный текст на чанки, генерировать векторные эмбеддинги и записывать их в Векторную базу данных.
* **[FR-02.6]** Система должна отображать текущий статус обработки медиафайла (`Загрузка` $\rightarrow$ `Извлечение аудио` $\rightarrow$ `Транскрипция` $\rightarrow$ `Индексация` $\rightarrow$ `Готово` / `Ошибка`).

### Детализированный Use Case (UC-02)
* **Название:** Загрузить и обработать медиафайл в базу знаний
* **Актор:** Администратор
* **Предусловия:**
  1. Администратор авторизован в панели управления с ролью `Admin`.
* **Постусловия:**
  * **Успех:** Медиафайл сохранен в Базу данных, расшифрованный текст индексирован в векторной БД, статус файла помечен как `Готово`.
  * **Неудача:** Статус файла помечен как `Ошибка`, в лог выведена причина сбоя, некорректные или недописанные векторы удалены из БД.

### Основной поток (Happy Path):
1. Администратор перетаскивает видеофайл `meeting.mp4` в область загрузки админ-панели.
2. Система проверяет формат файла и его размер.
3. Система загружает файл в Базу данных и создает запись в БД со статусом `Загрузка`.
4. Асинхронный фоновый воркер забирает файл и меняет статус на `Извлечение аудио`.
5. Воркер извлекает аудиодорожку в формате WAV.
6. Воркер передает аудио в модуль Whisper, изменяя статус на `Транскрипция`.
7. Полученный текст расшифровки разбивается на смысловые фрагменты (чанки).
8. Система генерирует эмбеддинги для чанков, сохраняет их в векторную БД и меняет статус файла на `Готово`.

### Альтернативные и исключительные потоки:
* **2a. Загружен файл недопустимого формата (например, .AVI) или размером > M МБ:**
  * Система отклоняет файл на этапе клиента/API и выводит уведомление: «Неподдерживаемый формат или превышен размер (макс. M МБ)». Сценарий завершается.
* **6a. Модуль распознавания речи вернул ошибку (например, аудиозапись пустая или повреждена):**
  * Воркер переводит статус документа в состояние `Ошибка`, сохраняет текст ошибки и отправляет уведомление администратору. Сценарий завершается.

### Критерии приемки
* **AC-02.1 Валидация формата и размера:**
  * **Given:** Администратор выбрал файл `archive.zip` размером 1 МБ.
  * **When:** Файл перетаскивается в область загрузки.
  * **Then:** Система НЕ загружает файл на сервер и отображает текст ошибки: «Неподдерживаемый формат файла.».
* **AC-02.2 Обработка видеофайла:**
  * **Given:** Выбран файл `presentation.mp4` (размер 5 МБ, длина 10 минут).
  * **When:** Администратор подтверждает загрузку.
  * **Then:** Файл переходит в статус `Загрузка`, затем `Транскрипция`, и в течение нескольких минут статус меняется на `Готово`, а расшифрованный текст становится доступным для поиска в чате.
* **AC-02.3 Чек-лист:**
  * [x] В таблице документов админ-панели отображается прогресс-бар обработки.
  * [x] Администратор имеет возможность отменить процесс обработки на любом этапе до момента записи в векторную БД.

### Нефункциональные требования
* **[NFR-02.1] Производительность:** Обработка и транскрипция 1 минуты аудио/видеозаписи не должна занимать более J секунд.
* **[NFR-02.2] Надежность:** Обработка медиафайлов должна быть с поддержкой повторных попыток при сетевых ошибках.

## US-03: Встраивание чат-бота на внешний сайт через HTML/JS-виджет
**Контекст (User Story):**
> Администратор системы желает получить готовый HTML/JS-код виджета в админ-панель и добавить его на внешний сайт компании,  
> Чтобы посетители внешнего сайта могли взаимодействовать с ботом без перехода в отдельное приложение.

> H - некие переменные, которые неизвестны на данном этапе развития. 

### Функциональные требования (FR)
* **[FR-03.1]** Система должна генерировать уникальный фрагмент JavaScript-кода для каждого зарегистрированного пользователя.
* **[FR-03.2]** JS-скрипт виджета должен инициализировать изолированный компонент.
* **[FR-03.3]** Виджет должен поддерживать передачу уникального идентификатора компании и токена сессии.
* **[FR-03.4]** Стили виджета не должны конфликтовать с CSS-стилями основного сайта, на который он встроен.

### Критерии приемки
* **AC-03.1 Инициализация виджета:**
  * **Given:** HTML-элемент <iframe> + токен в URL.
  * **When:** Страница внешнего сайта загружается в браузере.
  * **Then:** В на странице появляется виджет чата.
* **AC-03.2 Изоляция стилей:**
  * **Given:** На внешнем сайте заданы глобальные стили, localStorage, cookie и все они по умолчанию браузером изолированы.
  * **When:** Пользователь заходит на встроенный виджет бота.
  * **Then:** Кнопки внутри виджета сохраняют собственные фирменные стили и внутренние системы не имеют доступ ко внешнему сайту.
* **AC-03.3 Чек-лист:**
  * [x] Виджет загружается в первые H секунд после открытия сайта.

### Нефункциональные требования
* **[NFR-03.1] Безопасность:** Запросы от виджета к бэкенду должны защищаться CORS-политиками и валидироваться по разрешенному списку доменов.
* **[NFR-03.2] Время загрузки:** Скрипт виджета должен загружаться асинхронно, не блокируя рендеринг основного сайта.

## US-04: Загрузка и индексация текстовых и табличных документов (PDF, DOCX, XLSX, TXT, MD)
**Контекст (User Story):**
> Администратор базы знаний хочет загружать текстовые файлы, регламенты и электронные таблицы в форматах PDF, DOCX, XLSX, TXT, MD в панель управления,  
> Чтобы система автоматически извлекала текстовое содержимое, сохраняла структуру таблиц и индексировала данные в векторной базе для поиска и генерации ответов сотрудникам и клиентам.

> S, C, O, T_parse — некие переменные, которые неизвестны на данном этапе развития (S — макс. размер файла в МБ, C — размер текстового чанка в токенах, O — перекрытие чанков в токенах, T_parse — макс. время обработки документа). </br>
> *Предварительно, поддерживаемые форматы: PDF, DOCX, XLSX, TXT, MD.

### Функциональные требования (FR)
* **[FR-04.1]** Система должна принимать файлы форматов * размером до S МБ через drag-and-drop интерфейс и диалоговое окно выбора файлов.
* **[FR-04.2]** Для текстовых документов * система должна извлекать текст с сохранением логической структуры (заголовки разделов, списки, нумерация, абзацы).
* **[FR-04.3]** Для электронных таблиц  и встроенных таблиц система должна выполнять структурированный парсинг с сохранением связей строк, столбцов и шапки таблицы.
* **[FR-04.4]** Система должна разбивать извлеченный текст на семантические фрагменты (чанки) фиксированного размера C токенов с перекрытием O токенов, связывая каждый чанк с метаданными (ID документа, имя файла, номер страницы/листа).
* **[FR-04.5]** Система должна генерировать векторные эмбеддинги для каждого фрагмента и записывать их в векторную базу данных.
* **[FR-04.6]** Система должна создавать Задание обработки и отображать прогресс жизненного цикла документа (`Загружен` $\rightarrow$ `Обрабатывается` $\rightarrow$ `Проиндексирован` / `Ошибка обработки`).

### Детализированный Use Case (UC-04)
* **Название:** Загрузить и проиндексировать текстовый или табличный документ
* **Актор:** Администратор базы знаний
* **Предусловия:**
  1. Администратор авторизован в панели управления с ролью `Admin`.
  2. Файл соответствует поддерживаемому перечню форматов * и не превышает размер S МБ.
* **Постусловия:**
  * **Успех:** Документ сохранен в хранилище, текст и таблицы разбиты на чанки и проиндексированы в векторной БД, статус документа изменен на `Проиндексирован`, статус задания — `Успешно завершено`.
  * **Неудача:** Статус документа помечен как `Ошибка обработки`, статус задания — `Завершено с ошибкой`, в журнал зафиксирована причина сбоя, некорректные эмбеддинги удалены из БД.

### Основной поток (Happy Path):
1. Администратор перетаскивает файл регламента `policy.pdf` (или прайс-лист `prices.xlsx`) в область загрузки админ-панели.
2. Система валидирует допустимость формата и размер файла.
3. Система загружает файл в хранилище, создает сущность Документ со статусом `Загружен` и Задание обработки со статусом `Создано`.
4. Асинхронный воркер переводит статус документа в `Обрабатывается`, а задания — в `Выполняется`.
5. Модуль извлечения контента парсит текст, структуру заголовков и таблицы документа.
6. Система проверяет пригодность извлеченного текста к индексации (длина текста > 0, отсутствие нечитаемых бинарных данных).
7. Система производит чанкинг текста и формирует эмбеддинги для каждого фрагмента.
8. Система сохраняет эмбеддинги в векторную базу данных с метаданными принадлежности к организации и документу.
9. Система переводит документ в статус `Проиндексирован`, а задание — в `Успешно завершено`. Документ становится доступен для поиска в чате.

### Альтернативные и исключительные потоки:
* **2a. Загружен неподдерживаемый формат или размер превышает S МБ:**
  * Система отклоняет файл на этапе клиента/API и выводит уведомление: «Неподдерживаемый формат или превышен размер (макс. S МБ)». Сценарий завершается.
* **6a. Файл пуст либо представляет собой отсканированный образ без текстового слоя (текст не извлечен):**
  * Воркер переводит статус документа в `Ошибка обработки` с причиной «Файл не содержит пригодного для индексации текста», задание переходит в `Завершено с ошибкой`. Администратор получает уведомление. Сценарий завершается.
* **8a. Сбой векторной базы данных при сохранении эмбеддингов:**
  * Воркер откатывает частично записанные чанки, переводит документ в `Ошибка обработки`, в лог выводится стек ошибки.

### Критерии приемки
* **AC-04.1 (BDD — Негативный сценарий: пустой документ):**
  * **Given:** Администратор выбрал файл `empty.docx` размером 10 КБ, не содержащий печатного текста.
  * **When:** Файл отправляется на обработку в очередь.
  * **Then:** Система переводит документ в статус `Ошибка обработки`, выводит в таблице документов причину «Содержимое непригодно для индексации: текст отсутствует» и не создает векторов в БД.
* **AC-04.2 (BDD — Позитивный сценарий: обработка таблицы):**
  * **Given:** Администратор загрузил файл `tariffs.xlsx` с таблицей стоимости услуг компании.
  * **When:** Документ переходит в статус `Проиндексирован`.
  * **Then:** При вопросе пользователя в чате «Сколько стоит тариф Премиум?» система находит соответствующий чанк и формирует корректный ответ со ссылкой на `tariffs.xlsx`.
* **AC-04.3 (Чек-лист):**
  * [x] В админ-панели отображаются метаданные файла: оригинальное имя, размер, тип и дата добавления.
  * [x] Реализована фильтрация списка документов по статусам (`Загружен`, `Обрабатывается`, `Проиндексирован`, `Ошибка обработки`).

### Нефункциональные требования

## US-05: Озвучивание ответов ассистента (Text-to-Speech)
**Контекст (User Story): Как Пользователь (Сотрудник или Клиент).**
> Я хочу иметь возможность прослушать аудиоверсию сгенерированного ответа бота по нажатию кнопки воспроизведения,  
> Чтобы воспринимать информацию на слух при выполнении параллельных задач, в дороге или при ограничениях чтения текста с экрана.

> T_tts — максимальное время ожидания начала генерации аудиопотока в секундах.

### Функциональные требования (FR)
* **[FR-05.1]** Система должна отображать кнопку с иконкой аудио («Озвучить») рядом с каждым сгенерированным текстовым сообщением бота.
* **[FR-05.2]** По нажатию кнопки система должна отправлять неизменяемый снимок текста ответа (snapshot) во внешний сервис синтеза речи (TTS API), очищая текст от технической Markdown-разметки (BR14).
* **[FR-05.3]** Система должна предоставлять встроенный веб-аудиоплеер с элементами управления: старт/пауза, полоса воспроизведения и регулятор громкости.
* **[FR-05.4]** Система должна сохранять сгенерированный аудиофайл в кэше с привязкой к ID сообщения, предотвращая повторные обращения к TTS API при повторном воспроизведении пользователем.
* **[FR-05.5]** При недоступности TTS API или сетевом сбое система должна выводить уведомление о невозможности воспроизведения, не нарушая целостность и видимость текстового ответа (BR14).

### Детализированный Use Case (UC-05)
* **Название:** Воспроизвести аудиоверсию ответа бота
* **Актор:** Пользователь
* **Предусловия:**
  1. Пользователь находится в чате и получил сгенерированный ответ от бота.
  2. Генерация текста ответа полностью завершена.
* **Постусловия:**
  * **Успех:** Аудиофайл успешно синтезирован и воспроизводится плеером, аудио сохранено в кэше.
  * **Неудача:** Пользователь видит всплывающее сообщение о сбое аудиосервиса, текстовый ответ остается доступным для чтения.

### Основной поток:
1. Пользователь нажимает на кнопку «Озвучить» под сообщением бота.
2. Кнопка переходит в состояние загрузки (spinner).
3. Система проверяет наличие сгенерированного аудио в кэше.
4. При отсутствии кэша система отправляет очищенный текст в сервис синтеза речи TTS.
5. Модуль TTS возвращает сжатый аудиопоток.
6. Система сохраняет результат в кэш и передает поток в клиентский плеер.
7. Плеер автоматически начинает воспроизведение, иконка кнопки меняется на «Пауза / Стоп».

### Альтернативные и исключительные потоки:
* **3a. Аудиозапись уже закэширована:**
  * Система немедленно инициирует воспроизведение без сетевого запроса к внешней AI-системе TTS.
* **5a. Ошибка TTS API (таймаут или невалидный API-ключ):**
  * Система прерывает ожидание, сбрасывает индикатор загрузки и показывает тост-уведомление: «Сервис озвучивания временно недоступен». Текст ответа в чате остается неизменным.

### Критерии приемки
* **AC-05.1 (BDD — Негативный сценарий при сбое TTS):**
  * **Given:** Пользователь нажал кнопку «Озвучить» у ответа бота.
  * **When:** Внешний сервис TTS недоступен или вернул ошибку с кодом 5xx.
  * **Then:** Система прекращает ожидание, отображает всплывающее уведомление «Не удалось воспроизвести аудио», а текстовый ответ и диалог остаются полностью доступными.
* **AC-05.2 (BDD — Позитивный сценарий совпадения текста и речи):**
  * **Given:** Ответ бота содержит текст «Срок согласования заявления составляет 3 рабочих дня».
  * **When:** Пользователь нажимает кнопку воспроизведения аудио.
  * **Then:** Начинается воспроизведение речи, произносящей в точности «Срок согласования заявления составляет 3 рабочих дня» без искажения фактов.
* **AC-05.3 (Чек-лист):**
  * [x] Пользователь имеет возможность в любой момент приостановить (пауза) или остановить воспроизведение.
  * [x] Повторное воспроизведение того же сообщения не отправляет повторный запрос во внешнее TTS API (работает чтение из кэша).

### Нефункциональные требования
* **[NFR-05.1] Время до начала воспроизведения:** Задержка от момента клика до старта воспроизведения аудио не должна превышать T_tts секунд при p95.
* **[NFR-05.2] Формат аудиопотока:** Аудиоданные должны передаваться в сжатом формате с битрейтом, оптимизированным для быстрой загрузки по мобильным сетям.

## US-06: Актуализация и удаление материалов базы знаний
**Контекст (User Story):**
> Администратор базы знаний хочет удалять неактуальные документы и запускать переиндексацию обновленных версий файлов,  
> Чтобы корпоративная база знаний всегда предоставляла сотрудникам и клиентам достоверные сведения, а удаленные и устаревшие регламенты не использовались в ответах без простоя сервиса.

> T_del — максимальное время в секундах, за которое удаленный документ полностью исключается из поисковой выдачи.

### Функциональные требования (FR)
* **[FR-06.1]** Система должна предоставлять администратору функции «Переиндексировать» и «Удалить» для каждого документа в реестре базы знаний.
* **[FR-06.2]** При запуске переиндексации система должна создавать Задание обработки и переводить статус документа в `Повторная обработка`, сохраняя доступность ранее опубликованной версии для поисковых запросов пользователей до завершения процесса (BR8).
* **[FR-06.3]** При успешном завершении конвейера переиндексации система должна атомарно заменить старые векторные чанки новыми и вернуть документ в статус `Проиндексирован` (BR8).
* **[FR-06.4]** При сбое в процессе переиндексации система должна оставить прежнюю опубликованную версию активной в поиске, вернуть статус документа в `Проиндексирован`, а на Задании обработки зафиксировать статус `Завершено с ошибкой` и причину сбоя (BR8, BR15).
* **[FR-06.5]** При подтверждении удаления документа система должна отменить все активные фоновые задания этого документа, исключить документ из подборки материалов для ответов (BR7), перевести его в статус `Удалён` и удалить его физические файлы и векторы из базы данных.
* **[FR-06.6]** Сообщения в истории диалогов, сформированные до удаления документа и ссылающиеся на него, должны сохраняться с пометкой первоисточника «Материал архивирован/удален» (BR7, BR12).

### Детализированный Use Case (UC-06)
* **Название:** Актуализировать или удалить документ базы знаний
* **Актор:** Администратор базы знаний
* **Предусловия:**
  1. Администратор авторизован в системе с ролью `Admin`.
  2. Документ находится в статусе `Проиндексирован` или `Ошибка обработки`.
* **Постусловия:**
  * **Успех (Переиндексация):** Новая версия материалов опубликована целиком, документ сохраняет статус `Проиндексирован`, Задание имеет статус `Успешно завершено`.
  * **Успех (Удаление):** Документ переведен в статус `Удалён`, материалы удалены из векторной базы, новые ответы не содержат сведений из этого документа.
  * **Неудача:** Прежняя версия документа продолжает обслуживаться (при переиндексации) либо зафиксирована ошибка удаления, требующая повтора действия.

### Основной поток A (Переиндексация — Happy Path):
1. Администратор выбирает документ и нажимает кнопку «Переиндексировать».
2. Система создает Задание обработки с типом операции `reindex` в статусе `Создано`, документ переходит в статус `Повторная обработка`.
3. Система запускает полный фоновый конвейер обработки документа (извлечение текста/транскрипция, проверка пригодности, чанкинг, генерация эмбеддингов).
4. Во время обработки входящие запросы пользователей к чату продолжают обслуживаться с использованием предыдущей опубликованной версии документа.
5. Новые эмбеддинги успешно подготовлены. Система атомарно перезаписывает данные документа в векторной БД.
6. Статус документа обновляется на `Проиндексирован`, а Задание переходит в `Успешно завершено`.

### Основной поток B (Удаление — Happy Path):
1. Администратор нажимает кнопку «Удалить» в строке документа.
2. Система выводит предупреждающее модальное окно с запросом подтверждения.
3. Администратор подтверждает удаление.
4. Система создает Задание с типом операции `delete` и отменяет любые активные фоновые задания, связанные с данным документом.
5. Система немедленно переводит статус документа в `Удалён` и исключает его из выборки для формирования ответов RAG.
6. Система физически удаляет векторные индексы и исходный файл из хранилища. Задание переходит в `Успешно завершено`.

### Альтернативные и исключительные потоки:
* **3a. Сбой во время фоновой переиндексации:**
  * Воркер фиксирует сбой: Задание переводится в `Завершено с ошибкой`, статус документа возвращается в `Проиндексирован`. Прежняя опубликованная версия остается активной, пользователи не теряют доступ к материалу.
* **4a. Попытка удаления документа во время выполнения активного задания обработки:**
  * Система перехватывает сигнал отмены, прерывает выполнение задания парсинга/индексации и выполняет каскадное удаление данных.

### Критерии приемки
* **AC-06.1 (BDD — Непрерывность обслуживания во время переиндексации):**
  * **Given:** Документ «Регламент_отпусков.pdf» находится в процессе переиндексации (статус `Повторная обработка`).
  * **When:** Сотрудник задает в чате вопрос по правилам оформления отпусков.
  * **Then:** Система успешно формирует ответ на основе ранее проиндексированной версии регламента без сбоев и отказов.
* **AC-06.2 (BDD — Исключение удаленного документа из выдачи):**
  * **Given:** Администратор подтвердил удаление документа «Старый_прайс_2024.xlsx» (документ в статусе `Удалён`).
  * **When:** Клиент задает вопрос о ценах, которые присутствовали только в удаленном прайсе.
  * **Then:** Система исключает удаленный файл из поиска и возвращает ответ: «К сожалению, в базе знаний компании нет информации для ответа на данный вопрос».
* **AC-06.3 (Чек-лист):**
  * [x] Нажатие кнопки «Удалить» открывает окно подтверждения с явным перечислением последствий.
  * [x] Удаление документа приводит к отмене связанных незавершенных заданий в очереди воркеров.

### Нефункциональные требования
* **[NFR-06.1] Атомарность переиндексации:** Замена старых векторных индексов новыми должна происходить атомарно в рамках одной транзакции (zero-downtime).
* **[NFR-06.2] Скорость отзыва:** Удаленный документ должен прекращать участвовать в формировании новых ответов RAG не более чем через T_del секунд после подтверждения удаления.

## US-07: Просмотр и управление историей диалогов

* **AC-07.3 (Чек-лист):**

## US-08: Прозрачность ответов и ссылки на первоисточники (Source Attribution)

* **[FR-08.2]** В интерфейсе чата под текстом сгенерированного ответа система должна отображать интерактивный блок «Источники» со списком карточек первоисточников.
* **[FR-08.3]** Каждая карточка источника должна содержать имя исходного файла, его расширение, номер страницы/листа (для документов) или таймкод фрагмента (для аудио/видео).
* **[FR-08.4]** По клику на карточку источника система должна открывать окно быстрого просмотра с подсвеченным текстовым фрагментом (цитатой), на базе которого был дан ответ.
* **[FR-08.5]** Если в базе знаний не нашлось подходящей информации («сведений недостаточно»), ответ выводится без блока источников с явным уведомлением о нехватке данных (BR9, BR10).

### Критерии приемки
* **AC-08.1 (BDD — Отображение ссылок на источники):**
  * **Given:** В базе знаний проиндексирован документ «Положение_об_оплате_труда.pdf».
  * **When:** Пользователь спрашивает «В каких числах выплачивается заработная плата?».
  * **Then:** Бот выдает текстовый ответ, а под сообщением отображается кликабельная плашка «Положение_об_оплате_труда.pdf, стр. 5».
* **AC-08.2 (BDD — Просмотр цитаты из первоисточника):**
  * **Given:** Под ответом бота отображается плашка источника.
  * **When:** Пользователь кликает по плашке источника.
  * **Then:** Открывается модальное окно с отображением точной цитаты из регламента компании, использованной при генерации ответа.
* **AC-08.3 (Чек-лист):**
  * [x] В блоке источников выводятся только документы, находящиеся в статусе `Проиндексирован`.
  * [x] Ссылки на первоисточники сохраняются в истории сообщений и доступны при последующих сессиях.

### Нефункциональные требования
* **[NFR-08.1] Фактологическая точность:** Утверждения бота должны строго подтверждаться найденными фрагментами первоисточников без выдумывания фактов (BR9).
* **[NFR-08.2] Производительность интерфейса:** Рендеринг блока источников не должен задерживать начало стриминга текста ответа пользователю.

## US-09: Ролевое разграничение доступа и изоляция данных организаций (Multi-tenancy & RBAC)
**Контекст (User Story):**
> Как Администратор организации, я хочу иметь систему разграничения прав доступа и строгую изоляцию данных тенантов,  
> Чтобы сотрудники и клиенты одной компании не имели доступа к материалам другой компании, а управлять базой знаний могли только уполномоченные администраторы.

### Функциональные требования (FR)
* **[FR-09.1]** Система должна поддерживать ролевую модель разграничения прав с как минимум двумя ролями: `Администратор` (Admin) и `Пользователь` (User / Employee / Client).
* **[FR-09.2]** Все сущности системы (документы, векторные индексы, задания обработки, диалоги и виджеты) должны быть строго ассоциированы с идентификатором организации (`organization_id`).
* **[FR-09.3]** Поисковый RAG-конвейер должен автоматически фильтровать векторные фрагменты строго по `organization_id` текущего пользователя, исключая попадание материалов других компаний в выдачу (BR3).
* **[FR-09.4]** Любые операции добавления, переиндексации, удаления документов и конфигурирования виджета должны блокироваться на уровне API при отсутствии роли `Admin` (BR11).
* **[FR-09.5]** Система должна осуществлять аутентификацию пользователей по протоколам безопасной авторизации (JWT-токены) с проверкой срока жизни сессии и прав доступа к ресурсам (BR2).

### Критерии приемки
* **AC-09.1 (BDD — Изоляция баз знаний организаций):**
  * **Given:** Пользователь А принадлежит Организации 1, а в базе знаний Организации 2 загружен конфиденциальный файл «Финансовый_отчет.xlsx».
  * **When:** Пользователь А вводит в чате вопрос «Какова прибыль за прошлый квартал?».
  * **Then:** Векторный поиск выполняется исключительно по индексам Организации 1; данные Организации 2 ни при каких условиях не попадают в контекст ответа.
* **AC-09.2 (BDD — Запрет административных действий обычному пользователю):**
  * **Given:** Пользователь авторизован в системе с ролью `User`.
  * **When:** Пользователь пытается отправить запрос на удаление документа по API `DELETE /api/documents/{id}`.
  * **Then:** Система возвращает HTTP статус 403 Forbidden с сообщением «Недостаточно полномочий для управления базой знаний», и состояние документа не изменяется.
* **AC-09.3 (Чек-лист):**
  * [x] Навигационное меню админ-панели скрыто в интерфейсе для пользователей без роли `Admin`.
  * [x] Запросы между виджетом и бэкендом валидируются по привязанному идентификатору организации.

### Нефункциональные требования
* **[NFR-09.1] Безопасность данных:** Изоляция тенантов на уровне базы данных гарантирует невозможность межорганизационной утечки данных при любых сбоях клиентских фильтров.
* **[NFR-09.2] Защита сессий:** Токены авторизации должны быть зашифрованы и храниться в защищенных cookies (`HttpOnly`, `SameSite=Strict`, `Secure`).

## US-10: Прикрепление документа напрямую в чат для контекстного анализа
**Контекст (User Story): Как Пользователь (Сотрудник или Клиент).**
> Я хочу иметь возможность прикрепить файл (PDF, DOCX, XLSX или TXT) непосредственно в поле ввода чата,  
> Чтобы ассистент быстро проанализировал документ и ответил на мои вопросы конкретно по его содержимому в рамках текущей беседы.

> F_chat — максимальный размер файла, прикрепляемого в чат, в МБ. T_quick — максимальное время экспресс-обработки файла в секундах.

### Функциональные требования (FR)
* **[FR-10.1]** Поле ввода чата должно содержать кнопку с иконкой скрепки («Прикрепить файл») и поддерживать перетаскивание файлов методом drag-and-drop.
* **[FR-10.2]** Система должна валидировать тип прикрепляемого файла (PDF, DOCX, XLSX, TXT) и его размер (не более F_chat МБ).
* **[FR-10.3]** Прикрепленный файл должен регистрироваться в системе и проходить экспресс-конвейер извлечения текста и индексации в контексте текущего диалога (BR1, BR4).
* **[FR-10.4]** Система должна визуализировать статус обработки прикрепленного файла над полем ввода («Загрузка...» $\rightarrow$ «Обработка файла...» $\rightarrow$ «Готов к анализу»).
* **[FR-10.5]** При генерации ответа система должна учитывать извлеченное содержимое прикрепленного файла в качестве приоритетного контекста для LLM.

### Критерии приемки
* **AC-10.1 (BDD — Вопрос по прикрепленному файлу):**
  * **Given:** Пользователь прикрепил в чат файл «Трудовой_договор_проект.docx» и ввел вопрос «Какой установлен оклад?».
  * **When:** Пользователь нажимает кнопку «Отправить».
  * **Then:** Система извлекает данные из прикрепленного файла и формулирует ответ с точным указанием суммы оклада из текста договора.
* **AC-10.2 (BDD — Негативный сценарий превышения размера):**
  * **Given:** Пользователь пытается прикрепить файл размером F_chat + 5 МБ.
  * **When:** Файл выбран в диалоговом окне.
  * **Then:** Система блокирует загрузку и отображает подсказку: «Превышен максимальный размер файла для чата (лимит F_chat МБ)».
* **AC-10.3 (Чек-лист):**
  * [x] Пользователь может удалить ошибочно прикрепленный файл (иконка крестика) до нажатия кнопки «Отправить».
  * [x] Название прикрепленного файла отображается в карточке сообщения в истории переписки.

### Нефункциональные требования
* **[NFR-10.1] Время экспресс-обработки:** Подготовка контекста небольшого документа (до 10 страниц) в чате не должна превышать T_quick секунд.
